# Generated Frontend Data

Files in this directory are derivative inputs for the Svelte application. They
must never become the source of truth for network, policy, controller, I/O, or
process behavior.

`process-view.json` remains marked `bootstrap`. It establishes the process
presentation contract but is not yet regenerated from the canonical appliance
records, area topology, or IEC 61131-3 references.

`appliance-configs.json` is generated by Rust from 162 canonical appliance and
208 canonical connection YAML files. It contains versioned appliance and
connection summaries, port hardware and state, Rust-derived connector
properties, node and appliance-to-connection indexes, source revisions, and
the original source text used by the configuration views. The generated
catalog schema is `0.8.0`; its embedded source files use appliance schema
`0.9.0` and connection schema `0.2.0`. Appliance summaries include optional
Rapid-PVST bridge identity, LACP groups, reciprocal multi-chassis metadata,
and reciprocal firewall-HA roles when configured.

Canonical identifies the owning input files, not engineering completeness. The
current configuration values and architecture relationships are provisional
placeholders and will be revised as executable communication and scenario
requirements are implemented.

Svelte may use presentation-only coordinates and interaction state. It must not
invent missing devices, links, policy decisions, simulation values, or parser
results.

Schema `0.2.0` distinguishes the physical vPLC host cluster from logical
area-controller workloads and includes a local distributed-I/O station in every
process area.

## Current and Planned State

`process-view.json` is manually maintained and validated only by the frontend
schema guard and build checks. `appliance-configs.json` is structurally
validated and atomically generated by
`cargo run -p hearthline-cli -- config-generate` or after a successful
localhost API edit. The connection records are validated topology inputs. Rust
can now assemble 28 selected scenario paths and produce formal per-hop
communication traces through configured ports and media. These cover
independent Customer PC-01 and PC-02 public paths, Business IT PC-01 through
PC-04 internal DNS and HTTPS, approved or denied factory operations-data transfer,
three controlled WAF denials, one customer access-circuit outage, and one
Business IT Core-02 failover recovery, one converged northbound-firewall
recovery, one protocol-timed firewall session-continuity run, one HA-sync-loss
continuity run, one fail-closed standby-session-state-loss run, and one
long-idle continuity run in which retained state expires at the modeled TCP
deadline before the reverse packet is rejected, plus one fenced-isolation run
that retains a single active owner when peer failure is unconfirmed. Svelte
also consumes one composite factory-autonomy report that combines loss of both
factory-facing conduit handoffs with an operational local HMI-to-actuator
command path. Svelte consumes those reports in the simulation workspace and
endpoint sessions. Each
workstation profile reads its identity and network state from appliance YAML;
its browser home is selected from a compatible canonical HTTPS scenario. The
browsers render the bounded HTTP documents returned through the configured
service paths. Complete executable topology and control-source generation
remain future work.

The generated appliance data marks all ten process-area HMIs as interactive
and carries controller, command-tag, sensor-initial-value, actuator-state, and
safety facts into inspection. The HMI API reads canonical YAML directly and
executes each command chain in Rust; the generated JSON remains presentation
metadata, not process state.
