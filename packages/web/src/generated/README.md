# Generated Frontend Data

Files in this directory are derivative inputs for the Svelte application. They
must never become the source of truth for network, policy, controller, I/O, or
process behavior.

`process-view.json` is generated by Rust from the validated process-topology
YAML and canonical appliance repository. It carries ten process areas, five
support nodes, semantic network edges, ordered material flow, and the eight
representative nine-appliance area contracts. Body Preparation and Forming
keep overview metadata there while their detailed inventories come from the
canonical appliance catalog.

`appliance-configs.json` is generated by Rust from 394 canonical appliance and
450 canonical connection YAML files. It contains versioned appliance and
connection summaries, port hardware and state, Rust-derived connector
properties, node and appliance-to-connection indexes, source revisions, and
the original source text used by the configuration views. The generated
catalog schema is `0.9.0`; its embedded source files use appliance schema
`0.10.0` and connection schema `0.2.0`. Appliance summaries include optional
Rapid-PVST bridge identity, LACP groups, reciprocal multi-chassis metadata,
and reciprocal firewall-HA roles when configured.

Canonical identifies the owning input files, not engineering completeness. The
current configuration values and architecture relationships are provisional
placeholders and will be revised as executable communication and scenario
requirements are implemented.

Svelte may use presentation-only coordinates and interaction state. It must not
invent missing devices, links, policy decisions, simulation values, or parser
results.

Process-view schema `0.3.0` separates presentation topology from live process
state. Appliance schema `0.10.0` distinguishes the physical vPLC host cluster
from logical area-controller workloads and includes local distributed I/O in
every process area.

## Current and Planned State

Both JSON catalogs are structurally validated and atomically generated during
`hearthline model compile --locked`, `hearthline model lock --update`, or a
successful draft commit through the loopback API. Catalog digests are part of
`project/config/model.lock.json`; CI rejects drift. Svelte rejects a process
catalog not marked `generated`.
The connection records are validated topology inputs. Rust
can now assemble 30 selected scenario paths and produce formal per-hop
communication traces through configured ports and media. These cover
independent Customer PC-01 and PC-02 public paths, Business IT PC-01 through
PC-04 internal DNS and HTTPS, approved or denied factory operations-data transfer,
Forming historian collection and OT DMZ replication, three controlled WAF
denials, one customer access-circuit outage, and one
Business IT Core-02 failover recovery, one converged northbound-firewall
recovery, one protocol-timed firewall session-continuity run, one HA-sync-loss
continuity run, one fail-closed standby-session-state-loss run, and one
long-idle continuity run in which retained state expires at the modeled TCP
deadline before the reverse packet is rejected, plus one fenced-isolation run
that retains a single active owner when peer failure is unconfirmed. Svelte
also consumes one composite factory-autonomy report that combines loss of both
factory-facing conduit handoffs with an operational local HMI-to-actuator
command path. Svelte consumes those reports in the simulation workspace and
endpoint sessions. Each
workstation profile reads its identity and network state from appliance YAML;
its browser home is selected from a compatible canonical HTTPS scenario. The
browsers render the bounded HTTP documents returned through the configured
service paths. The full topology compiles into an immutable graph, but
arbitrary-path execution and broader control-source execution remain future
work.

The generated appliance data marks 17 process operator interfaces as
interactive and carries controller, command-tag, signal-scope,
sensor-initial-value, actuator-state, and safety facts into inspection. This
includes the three local Body Preparation HMIs plus the Forming machine PC,
four mould HMIs, and robot pendant. The HMI API reads canonical YAML directly.
Body Preparation executes changing mass, quality, phase, pipeline, and output state;
Forming gives its six interfaces one shared Rust cell state that executes the
accelerated ceramic-slip
pressure-casting cycle and projects changing signals, outputs, transfer
positions, guard state, alarms, faults, scan count, and cycle count. The
generated JSON remains presentation metadata, not process state.
The local API samples Forming state into bounded factory-local and OT DMZ
historian stores through two canonical network scenarios. The authorized
Forming SCADA publication action uses the latest DMZ record for the canonical
factory operations-data scenario. Neither the generated catalog nor scenario
YAML is rewritten by collection, replication, or publication.
